How it works

  1. 01

    The server builds the screen

    A backend, a CMS, or simply a JSON file in cloud storage describes the components and their content: a banner, a heading, a button. Different users, segments or experiments can get different payloads.

  2. 02

    The app fetches and caches it

    The app downloads the payload, keeps the last good copy, and redraws only when the payload actually changes.

  3. 03

    A renderer maps types to widgets

    Each type points to a native widget that already ships in the app. The server can arrange them, but it cannot add new code.

  4. 04

    Unknown types fall back

    An older app that meets a type it doesn't know skips it instead of crashing. Try the "New component" preset on v1.

Why frontend engineers should use it

Change UI without a release

On mobile, a release goes through store review and then waits for people to update. With SDUI, a copy change or a new banner reaches every user the next time they open the app.

Experiments and personalisation

Two segments can get two different payloads from the same build, so an A/B test doesn't need two app versions.

One source for every platform

Android, iOS and web read the same schema, so a campaign is defined once and looks the same everywhere.

Fast rollback

If a change goes wrong, the server sends the previous payload. Nobody waits for a hotfix build.

Engineers stop being the bottleneck

Product and marketing can change content within limits the engineers set, and engineers spend their time on components instead of copy changes.

Trade-offs

SDUI comes with trade-offs. It works best on screens that change often and stay fairly simple.

  • Versioning. Every component has to stay compatible with apps that are months old.
  • Debugging. A bug can live in the payload, the renderer or the data behind it, so you need good logging.
  • Performance. Parsing and building widgets at runtime takes time. Cache the payload and skip rebuilds when nothing changed.
  • Limits. The server can only use components the app already has. A truly new interaction still needs a release.
  • Offline. The app needs a bundled default or a cached copy for when there is no connection.
  • Safety. Treat the payload as data. Render text as text and only allow actions the app already knows.

What I learned building one

At Amartha I took the lending banners on the Flutter home screen from a prototype to server-driven UI in production. A few things mattered more than I expected.

  • Start with one surface. Banners were a good first target: they change often, and nothing breaks if one fails to load.
  • It doesn't need a paid service. The JSON lived in Firebase Storage, Remote Config told the app which file to load, and the app cached the last good copy. No new backend, no SDUI vendor, and no extra running cost.
  • Keep styling out of the payload. With a central theme config, the JSON says "title", not a font size, and the app stays on brand.
  • Rebuild only when the payload changes. Our first version re-parsed the banner every time the home screen rebuilt. Caching by payload removed the jank.
  • Always have a fallback. Unknown types, bad JSON and failed downloads should all end in a sensible screen, never a blank one.

      The queue Firestore already has

      You don't have to build the outbox above from scratch. Firestore keeps one for you; you mostly decide the document IDs and read the sync flag.

      • A write queue on the phone. With offline persistence (on by default on Android and iOS, opt-in on the web), every set, update and delete lands in the local cache first and waits in a queue on disk. The screen updates right away, and the queue survives an app restart.
      • Sent in order when the signal returns. The SDK sends pending writes in the order they were made. There is no retry code to write.
      • "Synced" is a flag you can read. Each snapshot carries hasPendingWrites. Listen with metadata changes to move a row from waiting to synced. Don't await the write itself offline: it only completes when the server confirms.
      • Pick the document ID on the phone. With one ID per job, a resend can only rewrite that same document; this is the idempotency key from the simulation. add() makes a new ID on every call, so a double tap on Submit still creates two records.
      • What it doesn't cover. Transactions need the server and fail offline. Photos don't belong in Firestore (1 MiB per document): Cloud Storage uploads them in chunks and can pause and resume. Work that must finish after the app is closed still needs WorkManager on Android or a background task on iOS.

    val ref = db.collection("repayments").document(job.id)
    ref.set(job.toMap())  // saved locally now, sent when online; don't await it offline

      Playground · Frame budget

      Smooth is a time budget.

      At 60 Hz the app has 16.7 ms to draw each frame, at 120 Hz only 8.3 ms. Put slow work on the main thread and frames miss the deadline, so the list stutters. Move it to a background thread and scrolling stays smooth.

      What keeps a real app smooth

      • Keep bind and build cheap. onBindViewHolder, a Compose item or a Flutter build() should only put values on screen. Parse, format and sort before the list asks for a row.
      • Move heavy work off the main thread. In Kotlin use withContext(Dispatchers.Default); in Flutter use Isolate.run for big JSON. Show a placeholder until the result arrives.
      • async is not a background thread. A Kotlin coroutine launched from viewModelScope runs on the main thread until withContext moves it. In Dart, await only waits: all code in an isolate shares the UI thread, which is fine for network calls but not for heavy CPU work.
      • Decode images at the size you show them. A 4000 px photo in a 48 px avatar wastes decode time and memory. Coil, Glide and Flutter's cacheWidth handle this.
      • Measure release builds on a real phone. Debug builds are slower. Use the Android Studio profiler or Perfetto, or the performance view in Flutter DevTools, and look for frames over the budget.
      • 120 Hz halves the budget. Work that fit at 60 Hz can start dropping frames on a 120 Hz phone.
      // Kotlin: parse off the main thread, then hand the rows to the list
val rows = withContext(Dispatchers.Default) { parseFeed(json) }
adapter.submitList(rows)

// Flutter: the same idea with an isolate
final rows = await Isolate.run(() => parseFeed(json));
setState(() => items = rows);

      Playground · Optimistic UI

      Show it now, confirm it later.

      Waiting for the server makes every tap feel slow. An optimistic app changes the screen right away, sends the request in the background, and undoes the change with a clear message if the server says no.

        When to be optimistic

        • Cheap to undo, usually succeeds. Likes, saves, mark as read, reorder and delete-with-undo are good fits. The user sees the result at once and almost never sees a rollback.
        • Never for money. Payments, transfers and bookings wait for the server and show progress. Showing "Paid" and taking it back later breaks trust.
        • Keep the confirmed value apart. Store what the server last confirmed next to what the screen shows. After several quick taps, a failed request rolls back to the confirmed value, not to whatever was on screen.
        • Say what happened. A rollback without a message looks like a bug. Put the item back where it was and tell the user why, with a way to try again.
        • It works with an offline queue. An optimistic change can wait in the outbox from the Offline sync tab; the same idempotency key keeps the retry safe.
        // Kotlin: show the like now, roll back only this post if the request fails
fun toggleLike(id: String) {
    val wasLiked = posts.value.first { it.id == id }.liked
    _posts.update { list -> list.setLiked(id, !wasLiked) }
    viewModelScope.launch {
        runCatching { api.setLiked(id, !wasLiked) }
            .onFailure {
                _posts.update { list -> list.setLiked(id, wasLiked) }
                _messages.emit(Message.LikeFailed(id))
            }
    }
}
